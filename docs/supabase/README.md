# Backend АНСДИМАТ: запуск и проверка

Серверная часть — Supabase: Postgres с построчным разграничением доступа,
авторизация по почте и функции выдачи прав. Расчёты остаются на устройстве —
сервер только хранит, синхронизирует и подтверждает доступ.

Без ключей приложение работает целиком локально: журналы, замеры и точки
лежат в SQLite на устройстве, а экран «Аккаунт» честно пишет, что
синхронизация не настроена.

## Что уже работает

| Возможность | Состояние |
|---|---|
| Регистрация, вход, выход | готово |
| Восстановление и смена пароля | готово |
| Удаление аккаунта из приложения | готово (требование сторов) |
| Синхронизация журналов, замеров и точек | готово |
| Разрешение расхождений между устройствами | готово, с выбором версии |
| Права на премиум-функции | готово, выдаёт сервер |
| Промокоды | готово |
| Оплата через магазины | не подключена, см. ниже |

## Локальный запуск

Нужен Docker.

```bash
npx supabase start
```

Команда поднимает Postgres, авторизацию и REST, применяет миграции из
`supabase/migrations` и печатает адреса с ключами. Скопируйте `API_URL` и
`ANON_KEY` в `.env`:

```
EXPO_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
EXPO_PUBLIC_SUPABASE_ANON_KEY=<ANON_KEY из вывода>
```

Дальше обычный запуск приложения:

```bash
npx expo start --web
```

Письма (подтверждение почты, сброс пароля) наружу не уходят — их видно в
почтовом ящике-заглушке на http://127.0.0.1:54324. Панель управления базой:
http://127.0.0.1:54323

Storage, Realtime и аналитика в локальной конфигурации отключены: проекту они
пока не нужны, а стартуют долго и роняют проверку готовности контейнеров.

## Бесплатное облако

Free-tier хватает и для MVP, и для показа заказчику: 500 МБ базы, 50 тыс.
активных пользователей в месяц. Ощутимое ограничение одно — после недели
простоя проект ставится на паузу и сам не просыпается: его возвращают кнопкой
Restore project в панели (в течение 90 дней). Платный Pro на паузу не ставится.

Коротко: завести проект на supabase.com, затем

```bash
npx supabase link --project-ref <ref-из-адреса-проекта> && npx supabase db push
```

и прописать `Project URL` с `anon public` ключом в `.env`.

**Подробный разбор — в [cloud-setup.md](./cloud-setup.md):** там по шагам, с
настройкой адресов возврата и почты, проверками против облака и разбором того,
что обычно ломается. Читать стоит его, а не эти четыре строки.

`anon`-ключ публичный и попадает в бандл — так и задумано. Данные закрывает
не секретность ключа, а политики доступа в базе. А вот `service_role` обходит
все политики, и в приложении его быть не должно.

## Проверки

Три сценария, все на живом сервере.

```bash
node supabase/tests/rls.test.js        # изоляция данных между учётками
node supabase/tests/sync.test.js       # протокол обмена и конфликты
CHROME_PATH=... node supabase/tests/e2e-sync.test.js   # приложение целиком
```

**`rls.test.js` — самый важный.** Он заводит две учётные записи и проверяет,
что вторая не видит и не может изменить данные первой. Политики доступа —
единственный барьер между данными клиентов; пока этот тест не проходит,
синхронизацию включать нельзя.

`e2e-sync.test.js` поднимает два браузерных контекста как два устройства:
регистрация на первом, журнал, обмен — и вход тем же аккаунтом на втором,
где журнал должен появиться. Переменная `CHROME_PATH` указывает на
установленный Chromium (`playwright-core` свой не скачивает).

## Как устроена синхронизация

```
1. PULL   строки, изменённые на сервере после прошлого обмена
2. MERGE  сравнение с локальными
3. PUSH   отправка всего, что помечено dirty
```

Три решения, без которых оно ломается в поле:

- **Время ставит сервер.** Часы на телефоне уходят, и по локальному времени
  запись «из будущего» навсегда выигрывала бы все сравнения.
- **Удаление мягкое** (`deleted_at`). Физически стёртую строку второе
  устройство, бывшее офлайн, не увидит — и зальёт обратно.
- **Расхождения не решаются молча.** Если запись менялась и там, и здесь,
  приложение показывает выбор версии. Потерять замеры, снятые в поле, —
  худшее, что оно может сделать.

Идентификаторы — UUID, генерируются на устройстве: журнал заводится офлайн
и должен без конфликтов лечь в общую таблицу.

Обмен запускается сам: при входе в аккаунт, при возвращении из фона (не чаще
раза в 15 минут) и через 30 секунд после последней правки. Вручную — кнопкой
на экране «Аккаунт», там же видно, сколько записей ждёт отправки.

## Права доступа

Премиум выдаёт функция `get_entitlements`, а не клиент. Ответ кэшируется на
сутки, чтобы подписка не отключалась без связи; в кэше лежит срок, выданный
сервером, поэтому подмена вскрывается при первом выходе в сеть.

Бесплатными остаются обработка ОФР и базовый калькулятор — это ядро
продукта. Подпиской закрыты синхронизация, барраж с утечками и экспорт.

Промокод на 12 месяцев заводится так:

```sql
insert into promo_codes (code, months, max_uses) values ('ANSDIMAT2026', 12, 50);
```

Пользователь вводит его в разделе «Аккаунт».

## Чего ещё нет

**Оплаты через App Store и Google Play.** Магазины не разрешают продавать
цифровой доступ мимо своей платёжной системы, поэтому кнопка «Подписаться»
сейчас честно объясняет, что оплата подключается, и предлагает промокод.
Схема уже рассчитана на биллинг: вебхук магазина пишет строку в
`subscriptions`, и права начинают выдаваться автоматически. Рекомендация по
провайдеру — в [`docs/backend-plan.md`](../backend-plan.md).

**Обмена журналами по ссылке.** Требует Storage, который сейчас отключён в
конфигурации локального стека.

**Аналитики и сбора ошибок.** Нужны сторонние аккаунты (PostHog, Sentry).
