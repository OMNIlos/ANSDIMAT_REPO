журналами между устройствами. Примерное время — 30–40 минут, из них половина
уходит на ожидание, пока поднимется проект.

## 1. Что уже сделано

Писать SQL руками не нужно. В репозитории лежат готовые миграции:

| Файл                               | Что создаёт                                                                                                                                     |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `20260729120000_core_schema.sql`   | таблицы `profiles`, `projects`, `measurements`, `observation_points`, политики доступа, автосоздание профиля при регистрации, удаление аккаунта |
| `20260729121000_subscriptions.sql` | `subscriptions`, `promo_codes`, функции `redeem_promo_code` и `get_entitlements`                                                                |
| `20260729122000_grants.sql`        | права Postgres для роли `authenticated`                                                                                                         |

Третий файл выглядит формальностью, но без него ничего не заработает.
Построчные политики (RLS) действуют **поверх** обычных прав Postgres: если роли
не выдан `select` на таблицу, запрос отвалится с 403 ещё до того, как политика
будет проверена. Это самая частая причина «схема залита, а приложение молчит».

Клиентская часть тоже готова: `AuthContext.js` — вход и восстановление пароля,
`sync/` — обмен данными, `billing/` — права на премиум-функции.

**Единственное, чего нет, — адреса вашего проекта и ключа.** Всё остальное
включится само, как только они появятся.

## 2. Границы бесплатного тарифа

На момент написания Free-tier даёт: 500 МБ базы, 5 ГБ исходящего трафика,
50 000 активных пользователей в месяц, 2 активных проекта на аккаунт. Актуальные
цифры — на supabase.com/pricing.

Для приложения такого профиля это очень много. Журнал ОФР со 100 замерами
занимает около 8 КБ, то есть в 500 МБ помещается порядка 60 тысяч журналов.
Упереться в лимит на демонстрации заказчику невозможно.

**Единственное ограничение, которое вы реально почувствуете:** проект
засыпает после недели без запросов. Просыпается сам при первом обращении, но
это занимает 10–30 секунд. Если планируете показ после долгого перерыва —
откройте приложение накануне.

## Шаг 1. Создать проект

1. Зарегистрируйтесь на supabase.com (проще всего через GitHub).
2. **New project**. Заполните:
   - **Name** — например, `ansdimat-mobile`;
   - **Database Password** — сгенерируйте длинный и **сохраните в менеджере
     паролей**. Он понадобится ровно один раз, на шаге 2, но восстановить его
     нельзя — только сбросить;
   - **Region** — ближайший к пользователям. Для СНГ это `Frankfurt (eu-central-1)`;
     регион влияет на задержку и после создания не меняется.
3. Дождитесь, пока проект поднимется — 2–3 минуты.

Ссылка на проект будет вида `https://supabase.com/dashboard/project/abcdefghijklmnop`.
Хвост `abcdefghijklmnop` — это **project ref**, он нужен на следующем шаге.

## Шаг 2. Залить схему

Из корня репозитория:

```bash
npx supabase login
```

Команда откроет браузер и попросит подтвердить доступ. Дальше связываем
локальный проект с облачным:

```bash
npx supabase link --project-ref <ваш-ref>
```

Спросит пароль базы — тот, что сохранили на шаге 1. Теперь заливаем схему:

```bash
npx supabase db push
```

Покажет список миграций и спросит подтверждение. После выполнения в панели
Table Editor появятся пять таблиц.

**Проверьте, что RLS включена:** в Table Editor у каждой таблицы должна стоять
пометка `RLS enabled`. Если её нет — миграция применилась не полностью, и данные
одного пользователя будут видны всем. Это единственная вещь на этой странице,
которую нельзя оставить «на потом».

## Шаг 3. Прописать ключи

**Project Settings → API Keys.** Понадобятся два значения:

- **Project URL** — `https://<ref>.supabase.co`
- **anon public** — длинный ключ, начинается с `eyJ...`

Скопируйте их в `.env` в корне репозитория (файл в git не попадает,
образец — в `.env.example`):

```
EXPO_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon public key>
```

Префикс `EXPO_PUBLIC_` обязателен — без него переменная не попадёт в приложение.

Для облачных сборок EAS `.env` недоступен, ключи задаются секретами — один раз
на проект:

```bash
eas secret:create --scope project --name EXPO_PUBLIC_SUPABASE_URL --value https://<ref>.supabase.co
```

```bash
eas secret:create --scope project --name EXPO_PUBLIC_SUPABASE_ANON_KEY --value <anon public key>
```

### Про то, какой ключ публичный

`anon` — публичный по замыслу. Он лежит в бандле открыто, и вытащить его из
APK может кто угодно. Это не дыра: он даёт ровно те права, что описаны в
политиках, а политики пускают пользователя только к своим строкам.

**`service_role` в приложение класть нельзя никогда.** Он обходит все политики
и открывает данные всех клиентов. Он нужен только серверным сценариям — вебхуку
магазина, административным скриптам. В `.env` мобильного приложения его быть
не должно.

## Шаг 4. Настроить вход и письма

### Адреса возврата

**Authentication → URL Configuration → Redirect URLs.** Добавьте:

```
ansdimat://reset-password
```

Схема `ansdimat` объявлена в [`app.json`](../../app.json), и по этому адресу
приложение открывается по ссылке из письма. Без записи в списке разрешённых
Supabase откажется отправлять письмо со сбросом, и восстановление пароля просто
не заработает — сообщения об ошибке пользователь при этом не увидит.

Если планируете и веб-версию, добавьте туда же её адрес.

### Подтверждение почты

**Authentication → Sign In / Providers → Email.**

- Для **показа заказчику** оставьте `Confirm email` выключенным: регистрация
  проходит в один шаг, ничего ждать не надо.
- Для **боевого запуска** включите. Иначе любой сможет зарегистрироваться на
  чужой адрес, а вы получите мёртвые аккаунты, которые нельзя восстановить.

### Почта — единственное, что придётся доделать

Встроенный отправитель Supabase рассчитан только на разработку: у него жёсткий
лимит порядка нескольких писем в час, и письма часто уходят в спам. На демо
этого хватит. Для реальных пользователей нужен свой SMTP —
**Project Settings → Authentication → SMTP Settings**.

Бесплатных вариантов достаточно: Resend (3 000 писем в месяц), Brevo, Postmark.
Понадобится домен, с которого будете отправлять, и записи SPF и DKIM в его DNS —
без них письма будут попадать в спам независимо от провайдера.

Пока SMTP не настроен, восстановление пароля работает, но ненадёжно. Это стоит
проговорить с заказчиком заранее, чтобы не выяснилось на защите.

### Длина пароля

**Authentication → Policies.** По умолчанию 6 символов; для боевого запуска
разумно поднять до 8 и включить проверку по базе утёкших паролей
(`Prevent use of leaked passwords`) — она бесплатная.

## Шаг 5. Проверить

Не «запустить и посмотреть», а прогнать три сценария против облака. Тесты
берут адрес из переменных окружения:

```bash
SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<anon> node supabase/tests/rls.test.js
```

**Этот тест — самый важный.** Он заводит две учётные записи и убеждается, что
вторая не видит и не может изменить данные первой. Политики доступа —
единственный барьер между данными разных клиентов; пока проверка не проходит,
синхронизацию включать нельзя.

```bash
SUPABASE_URL=https://iokljcwtrfejbzzyykug.supabase.co SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJzdXBhYmFzZSIsInJlZiI6Imlva2xqY3d0cmZlamJ6enl5a3VnIiwicm9sZSI6ImFub24iLCJpYXQiOjE3ODU3NDgwMTgsImV4cCI6MjEwMTMyNDAxOH0.K7rvR5tHKC8q7Lg-8eUFhJxOZTT5pMiBgeAqabDHGno node supabase/tests/sync.test.js
```

Проверяет протокол обмена: порядок заливки, мягкое удаление, распознавание
расхождений между устройствами.

Дальше — приложение целиком:

```bash
npx expo start --web
```

Зарегистрируйтесь, заведите журнал, откройте «Настройки → Аккаунт» и нажмите
синхронизацию. Затем откройте приложение в приватном окне браузера (это
считается вторым устройством), войдите тем же аккаунтом — журнал должен
приехать.

После регистрации загляните в **Table Editor → profiles**: там должна появиться
строка. Если её нет, значит не применился триггер `handle_new_user`, и
`db push` прошёл не полностью.

## Шаг 6. Промокод

Оплата через магазины пока не подключена (см.
[`backend-plan.md`](../backend-plan.md)), поэтому премиум-функции открываются
промокодом. Заведите его в **SQL Editor**:

```sql
insert into promo_codes (code, months, max_uses)
values ('ANSDIMAT2026', 12, 50);
```

Пользователь вводит код на экране «Аккаунт» и получает 12 месяцев доступа.
Для показа заказчику это удобнее всего: код можно выдать прямо на встрече.

Посмотреть, кто чем пользуется:

```sql
select code, months, max_uses, used_count from promo_codes;
select owner_id, platform, status, expires_at from subscriptions order by created_at desc;
```

## Что пойдёт не так

**Всё залилось, но приложение не видит сервера.** Проверьте, что переменные
называются ровно `EXPO_PUBLIC_SUPABASE_URL` и `EXPO_PUBLIC_SUPABASE_ANON_KEY`,
и **перезапустите** `expo start` — переменные окружения читаются при старте
бандлера, на лету не подхватываются.

**Запросы возвращают 403 при живой сессии.** Не применилась миграция с правами
(`20260729122000_grants.sql`). Повторите `npx supabase db push`.

**Письмо со сбросом пароля не приходит.** Три причины по частоте: адрес
`ansdimat://reset-password` не добавлен в Redirect URLs; исчерпан лимит
встроенного отправителя; письмо в спаме.

**Первый запрос после паузы висит полминуты.** Проект спал. Это штатное
поведение бесплатного тарифа, не ошибка.

**`db push` требует пароль, которого нет.** Сбросьте его в
Project Settings → Database → Reset database password. На данные это не влияет.

**Данные одного пользователя видны другому.** Немедленно проверьте RLS в
Table Editor и прогоните `rls.test.js`. До выяснения не давайте приложение
никому, кроме себя.
