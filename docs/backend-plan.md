## 1. Что уже есть

**На клиенте.**

- SQLite (`db/`) — источник истины: таблицы `projects`, `measurements`,
  `observation_points`, `settings`. Миграции по `PRAGMA user_version`,
  сейчас версия 2.
- `AuthContext` + `lib/supabase.js` — обёртка над Supabase Auth: вход,
  регистрация, выход, подписка на сессию. Работает, но не подключена:
  нет `.env` с ключами.
- `utils/SubscriptionManager.js` — статус подписки в AsyncStorage.
  Это заглушка: она ничего не проверяет и не списывает деньги.

**Чего нет вообще.** Синхронизации, серверной проверки покупок, обмена
журналами, аналитики, восстановления пароля, удаления аккаунта.

Дальше по тексту эта заглушка называется «текущий SubscriptionManager» —
её предстоит заменить целиком.

> **Статус на 2 августа 2026.** Этапы 1–3 выполнены: схема с политиками
> доступа лежит в `supabase/migrations`, синхронизация — в `sync/`, права —
> в `billing/`. Заглушка подписки удалена, `SubscriptionManager` больше нет.
> Не сделано только подключение платёжного провайдера и обмен журналами по
> ссылке. Порядок запуска и проверок — в
> [`docs/supabase/README.md`](./supabase/README.md).

## 2. Архитектурное решение

### Почему Supabase, а не свой сервер

| Критерий | Supabase | Свой backend (Node + Postgres) |
|---|---|---|
| Срок до первой версии | 1–2 недели | 6–10 недель |
| Аутентификация | из коробки, включая OAuth и восстановление | пишем сами |
| RLS на уровне БД | штатно | пишем сами или ORM-слой |
| Стоимость на старте | $0 → $25/мес | от $40/мес (сервер + БД + почта) |
| Приём вебхуков от сторов | Edge Functions | свои эндпоинты |
| Уход с платформы | Postgres выгружается дампом | не применимо |

Проект — нишевый инструмент с предсказуемо небольшой аудиторией
(гидрогеологи СНГ, сотни-тысячи активных пользователей). Своя инфраструктура
здесь не окупится, а Supabase — это обычный Postgres, из которого всегда можно
уехать дампом. Берём Supabase.

**Важная оговорка.** Расчёты остаются на устройстве. Сервер не считает
гидрогеологию — он хранит, синхронизирует и подтверждает права. Это не
техническое ограничение, а требование: приложение обязано работать в поле
без связи.

### Состав

```
Мобильное приложение (Expo)
        │
        ├── SQLite (офлайн, источник истины на устройстве)
        │
        └── Supabase
             ├── Auth               — аккаунты, сессии, восстановление пароля
             ├── Postgres + RLS     — журналы, замеры, точки, подписки
             ├── Storage            — экспортные файлы и вложения
             └── Edge Functions     — вебхуки сторов, выдача прав, экспорт
                      │
                      ├── App Store Server Notifications V2
                      └── Google Play Real-time Developer Notifications
```

## 3. Модель данных

Серверные таблицы повторяют локальные плюс поля синхронизации. Ключевое
отличие: у каждой записи есть `owner_id`, `updated_at` и `deleted_at`.

```sql
-- Профиль поверх auth.users: туда нельзя добавлять свои поля
create table profiles (
  id           uuid primary key references auth.users on delete cascade,
  display_name text,
  organization text,
  locale       text not null default 'ru',
  created_at   timestamptz not null default now()
);

create table projects (
  id               uuid primary key,
  owner_id         uuid not null references auth.users on delete cascade,
  name             text not null,
  ofr_type         text not null default 'single',
  q                double precision not null default 0,
  pumping_duration double precision not null default 0,
  starred          boolean not null default false,
  result_t         double precision,
  result_slope     double precision,
  result_method    text,
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now(),
  deleted_at       timestamptz            -- мягкое удаление, см. синхронизацию
);

create table measurements (
  id         uuid primary key,
  project_id uuid not null references projects on delete cascade,
  owner_id   uuid not null references auth.users on delete cascade,
  t          double precision not null,
  s          double precision not null,
  sort_order integer not null default 0,
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);

create table observation_points (
  id          uuid primary key,
  owner_id    uuid not null references auth.users on delete cascade,
  title       text not null,
  type        text not null default 'observation',
  lat         double precision not null,
  lon         double precision not null,
  note        text,
  recorded_at timestamptz not null,
  updated_at  timestamptz not null default now(),
  deleted_at  timestamptz
);

create index on projects (owner_id, updated_at desc);
create index on measurements (project_id, sort_order);
create index on observation_points (owner_id, updated_at desc);
```

**Идентификаторы.** UUID генерируются на устройстве. Это позволяет создавать
журналы офлайн и не ловить конфликты ключей при заливке — на клиенте уже
используется `createId()` в `db/index.js`, его надо перевести на UUID v4.

**Мягкое удаление.** Физическое удаление на одном устройстве невозможно
донести до второго, если оно офлайн: строки просто нет, и второе устройство
зальёт её обратно. Поэтому удаление ставит `deleted_at`, а чистка идёт
раз в сутки по расписанию — записи старше 90 дней удаляются физически.

### RLS

Политики пишутся один раз и закрывают всё:

```sql
alter table projects enable row level security;

create policy "видит только свои" on projects
  for select using (auth.uid() = owner_id);
create policy "создаёт только свои" on projects
  for insert with check (auth.uid() = owner_id);
create policy "правит только свои" on projects
  for update using (auth.uid() = owner_id);
```

Аналогично для остальных таблиц. `measurements` дополнительно проверяет, что
родительский проект принадлежит тому же владельцу.

**Проверка:** отдельный тест-скрипт заходит под двумя учётками и убеждается,
что вторая не видит и не может изменить данные первой. Без этого теста RLS
считать рабочей нельзя — это единственный барьер между данными клиентов.

## 4. Аккаунты

### Что нужно сверх существующего кода

| Функция | Состояние | Работы |
|---|---|---|
| Регистрация по e-mail | код есть | подключить ключи, включить подтверждение почты |
| Вход | код есть | — |
| Восстановление пароля | нет | экран + `resetPasswordForEmail` + deep link |
| Смена пароля | нет | экран в настройках |
| Удаление аккаунта | нет | **обязательно для App Store и Google Play** |
| Вход через Apple | нет | **обязателен, если есть любой другой соцвход** |
| Вход через Google | нет | по желанию |

**Удаление аккаунта — блокирующее требование сторов.** Apple отклоняет
приложения с регистрацией, где нельзя удалить учётку из самого приложения.
Реализация: Edge Function `delete-account` под сервисным ключом удаляет
пользователя, каскад в БД чистит данные, клиент чистит локальную SQLite.

**Подтверждение почты.** Включаем: без него любой может занять чужой адрес,
а восстановление пароля превращается в дыру.

### Deep links

Для подтверждения почты и сброса пароля нужна схема `ansdimat://` плюс
Universal Links на `ansdimat.com`. В `app.json` добавляется `scheme`, на сайт
кладутся `apple-app-site-association` и `assetlinks.json`.

## 5. Синхронизация

Самая сложная часть. Требование «работает в поле без связи» означает, что
клиент правит данные офлайн, а сервер должен принять их позже и разрешить
конфликты.

### Модель: pull-push по метке времени

```
1. PULL   GET  /projects?updated_at=gt.<last_sync>
2. MERGE  сравнить с локальными записями
3. PUSH   upsert локальных изменений с updated_at > last_sync
4. STAMP  записать новый last_sync (время сервера, не устройства)
```

**Время берётся серверное.** Часы на телефоне уходят, и по локальному времени
запись «из будущего» навсегда выиграет все конфликты.

### Разрешение конфликтов

Правило по умолчанию — **последняя запись побеждает** (LWW) на уровне строки.
Для этого проекта этого достаточно: журнал ведёт один человек, одновременная
правка одного опыта с двух устройств маловероятна.

Исключение — таблица замеров. Там LWW по строке даёт неприятный эффект:
если на одном устройстве добавили замеры 10–15, а на другом правили замер 3,
LWW по проекту снесёт одну из правок. Поэтому замеры синхронизируются
построчно по своему `id`, а не пачкой на проект.

**Что показываем пользователю.** Если сервер вернул запись новее локальной и
локальная тоже менялась после последней синхронизации — не молчим, а спрашиваем:
«Журнал изменён на другом устройстве. Оставить эту версию или загрузить ту?»
Молчаливая потеря замеров, снятых в поле, — худшее, что может сделать
приложение для полевых работ.

### Когда синхронизируем

- при входе в аккаунт — полная выгрузка;
- при открытии приложения, если прошло больше 15 минут;
- после правки — отложенно, через 30 секунд после последнего изменения;
- вручную — кнопкой в настройках, с показом времени последней синхронизации.

Автосинхронизация только по Wi-Fi — отдельная настройка: полевые работы часто
идут на дорогом мобильном трафике.

### Клиентская часть

Добавляется таблица `sync_state (table_name, last_pulled_at, last_pushed_at)`
и модуль `sync/` с очередью операций. Записи получают флаг `dirty`, который
снимается после успешного push.

## 6. Подписки и биллинг

### Что продаём

| План | Цена (ориентир) | Что даёт |
|---|---|---|
| Базовый | 0 | Обработка ОФР, калькулятор, дневник, локальное хранение |
| Профи, месяц | ~499 ₽ | Синхронизация, барраж, утечки, экспорт PDF/CSV, безлимит журналов |
| Профи, год | ~3 990 ₽ | То же, выгоднее на треть |

Цены в рублях, а не в долларах, как сейчас в коде: аудитория — СНГ.
Итоговые цифры за заказчиком.

### Почему нельзя оставить текущую реализацию

`SubscriptionManager` пишет статус в AsyncStorage. Любой пользователь с
рутованным устройством включает премиум за пять минут. Кроме того, магазины
не разрешают продавать цифровой контент мимо своей платёжной системы:
Apple берёт 15–30 %, Google столько же, и обойти это в приложении нельзя.

### Схема

```
Приложение
   │ покупка через expo-in-app-purchases / RevenueCat
   ▼
App Store / Google Play
   │ чек (receipt / purchase token)
   ▼
Edge Function verify-purchase
   │ проверяет чек в API магазина
   ▼
Таблица subscriptions ── права выдаёт сервер, не клиент
   ▲
   │ App Store Server Notifications V2
   │ Google Play RTDN (Pub/Sub)
   └── продление, отмена, возврат, льготный период
```

```sql
create table subscriptions (
  id                uuid primary key default gen_random_uuid(),
  owner_id          uuid not null references auth.users on delete cascade,
  platform          text not null check (platform in ('ios','android','promo')),
  product_id        text not null,
  original_tx_id    text not null,          -- ключ для связи продлений
  status            text not null,           -- active | grace | expired | refunded
  expires_at        timestamptz,
  auto_renew        boolean not null default true,
  environment       text not null default 'production',  -- sandbox | production
  raw_payload       jsonb,                   -- сырой ответ магазина
  updated_at        timestamptz not null default now(),
  unique (platform, original_tx_id)
);

create index on subscriptions (owner_id, status, expires_at desc);
```

**Права проверяются на сервере.** Клиент спрашивает `entitlements` и получает
готовый ответ, а не решает сам по локальному флагу.

### RevenueCat или свои функции

| | Свои Edge Functions | RevenueCat |
|---|---|---|
| Срок | 2–3 недели | 3–5 дней |
| Цена | $0 | бесплатно до $2,5к/мес выручки, далее 1 % |
| Что делать самим | верификация чеков, вебхуки, продления, возвраты, миграции | подключить SDK |
| Риск ошибок | высокий: у Apple и Google разные модели продлений | низкий |

**Рекомендация: начать с RevenueCat.** Биллинг — та область, где своя
реализация даёт баги, которые видит пользователь и оплачивает поддержка.
1 % от выручки дешевле недели разработчика. Переехать на свою реализацию
можно позже, схема таблиц не изменится.

### Что обязательно предусмотреть

- **Восстановление покупок** — обязательный пункт правил Apple; кнопка
  «Восстановить покупки» на экране подписки.
- **Льготный период** (grace period) — при сбое оплаты доступ сохраняется
  16 дней. Отключать премиум сразу — потерять клиента на ровном месте.
- **Возвраты** — по вебхуку `REFUND` статус переводится в `refunded`,
  доступ закрывается.
- **Sandbox** — тестовые покупки приходят с другого окружения; если не
  разделить, тестировщик выдаст себе вечную подписку в проде.
- **Промокоды** — платформа `promo` в таблице: для заказчика, партнёров,
  преподавателей. Заводится вручную через админку.

## 7. Разграничение доступа к функциям

Сейчас премиум-функции ничем не ограничены. Нужен единый список прав:

```js
// entitlements, выдаваемые сервером
{
  sync: true,           // синхронизация между устройствами
  advancedCalc: true,   // барраж, инфильтрационные утечки
  exportPdf: true,      // экспорт отчёта
  unlimitedProjects: true
}
```

Клиент кэширует ответ на 24 часа, чтобы в поле без сети премиум не отключался.
Кэш подписан сервером и содержит `expires_at`, поэтому подделать его на
устройстве нельзя — при следующем выходе в сеть подмена вскроется.

**Что закрывать, а что нет.** Обработка ОФР и базовый калькулятор остаются
бесплатными: это ядро продукта и то, ради чего приложение ставят. Платными
становятся синхронизация, расширенные расчёты и экспорт — то, что нужно
работающему на потоке специалисту, а не студенту.

## 8. Обмен журналами

Кнопка «поделиться» в списке журналов сейчас отдаёт файл. Серверная версия
даёт ссылку:

1. Клиент запрашивает Edge Function `share-project`.
2. Функция кладёт JSON журнала в Storage, создаёт запись `shared_links`
   с токеном и сроком жизни 30 дней.
3. Возвращает `https://ansdimat.com/s/<token>`.
4. Получатель открывает ссылку → deep link → приложение импортирует журнал.

```sql
create table shared_links (
  token      text primary key,
  project_id uuid not null references projects on delete cascade,
  owner_id   uuid not null references auth.users on delete cascade,
  expires_at timestamptz not null,
  opened_count integer not null default 0,
  created_at timestamptz not null default now()
);
```

Ссылка даёт копию журнала, а не доступ к аккаунту. Совместного редактирования
не делаем — для полевых журналов оно не нужно и сильно усложняет синхронизацию.

## 9. Аналитика и наблюдаемость

ТЗ требует «сбор базовой статистики использования». Минимум:

- **Продуктовая аналитика** — Amplitude или PostHog. События: запуск,
  создание журнала, расчёт выполнен, экспорт, открытие экрана подписки,
  покупка. Без персональных данных: идентификатор устройства, не почта.
- **Сбор ошибок** — Sentry с source maps: без него причину падения на чужом
  Android не найти.
- **Мониторинг Supabase** — алерты на рост 5xx и на приближение к квотам.

Сбор аналитики должен отключаться в настройках — этого требуют и правила
магазинов, и здравый смысл.

## 10. Безопасность и персональные данные

| Требование | Решение |
|---|---|
| Ключи в приложении | только `anon key` — он публичный по устройству; `service_role` живёт исключительно в Edge Functions |
| Пароли | хранит Supabase Auth (bcrypt), приложение их не видит |
| Доступ к чужим данным | RLS + тест на двух учётках |
| Координаты точек | персональные данные — храним только с согласия, даём удалить |
| Удаление аккаунта | Edge Function + каскад + чистка локальной БД |
| Политика конфиденциальности | обязательна для обоих сторов, публикуется на ansdimat.com |
| Data Safety / Privacy Nutrition Labels | заполняются в консолях: почта, координаты, идентификатор устройства |
| Хранение данных россиян | при работе на РФ — 152-ФЗ требует первичной базы в РФ; см. риск ниже |

**Риск по 152-ФЗ.** Supabase размещается в облаках вне РФ. Если аудитория
преимущественно российская и заказчик — юрлицо РФ, потребуется либо
self-hosted Supabase на российском хостинге (Selectel, Yandex Cloud), либо
своя инсталляция Postgres. Это решение нужно принять **до** запуска, потому
что переезд после набора базы пользователей стоит дорого. Технически
self-hosted Supabase — тот же набор образов, миграция схемы не меняется.

## 11. Окружения и релизный процесс

Три окружения: `dev` (локально), `staging` (тестовые сборки и sandbox-покупки),
`production`.

- Схема БД — миграциями через Supabase CLI, в гите, а не руками в панели.
- Секреты — в EAS Secrets, не в репозитории.
- Ветка `main` → staging автоматически, прод — по тегу.

```bash
supabase migration new add_subscriptions
supabase db push --db-url "$STAGING_DB_URL"
eas secret:create --name EXPO_PUBLIC_SUPABASE_URL --value ...
```

## 12. План работ по этапам

Оценка в человеко-днях для одного разработчика, знакомого с проектом.

### Этап 1. Аккаунты работают (5–7 дней)

| Задача | Дней |
|---|---|
| Создать проекты Supabase (staging + prod), ключи в EAS | 0,5 |
| Миграции: profiles, projects, measurements, observation_points, RLS | 1,5 |
| Тест RLS на двух учётках | 0,5 |
| Восстановление и смена пароля, экраны | 1 |
| Удаление аккаунта (Edge Function + экран) | 1 |
| Вход через Apple | 1 |
| Deep links, домен, AASA/assetlinks | 1 |

**Готово, когда:** можно зарегистрироваться, восстановить пароль и удалить
аккаунт; вторая учётка не видит данные первой.

### Этап 2. Синхронизация (8–10 дней)

| Задача | Дней |
|---|---|
| Перевод локальных id на UUID + миграция схемы v3 | 1 |
| Поля sync: updated_at, deleted_at, dirty; таблица sync_state | 1 |
| Модуль sync: pull, merge, push, серверное время | 3 |
| Разрешение конфликтов + экран выбора версии | 2 |
| Настройки: только по Wi-Fi, ручная синхронизация, время последней | 1 |
| Тесты: офлайн-правки на двух устройствах, конфликт, удаление | 2 |

**Готово, когда:** журнал, созданный офлайн на телефоне, появляется на
планшете после выхода в сеть; конфликт показывается, а не теряется.

### Этап 3. Подписки (6–8 дней)

| Задача | Дней |
|---|---|
| Товары в App Store Connect и Google Play Console | 1 |
| Подключение RevenueCat, SDK в приложении | 1,5 |
| Таблица subscriptions, вебхуки RevenueCat → Supabase | 1,5 |
| Entitlements: серверная выдача + кэш на клиенте | 1 |
| Переписать SubscriptionManager на реальные права | 1 |
| Восстановление покупок, льготный период, возвраты | 1 |
| Тесты в sandbox: покупка, продление, отмена, возврат | 1 |

**Готово, когда:** покупка в sandbox открывает премиум, отмена закрывает,
а подмена локального флага ничего не даёт.

### Этап 4. Остальное для релиза (5–6 дней)

| Задача | Дней |
|---|---|
| Обмен журналами по ссылке | 2 |
| Аналитика + Sentry | 1 |
| Политика конфиденциальности, Data Safety, Privacy Labels | 1 |
| Чистка мёртвого кода, дубли локализации | 1 |
| Нагрузочная проверка синхронизации на 10 тыс. замеров | 0,5 |

**Итого: 24–31 рабочий день** (5–6 недель) для одного разработчика.
С учётом ревью, правок и ожидания модерации в сторах — **8–10 недель**
до публикации.

### Что можно выпустить раньше

Если нужен APK заказчику быстрее, порядок такой: этап 1 → сборка →
показ. Синхронизация и подписки добавляются следующими версиями. Приложение
уже сейчас полноценно работает офлайн, а аккаунт нужен только для переноса
данных между устройствами.
