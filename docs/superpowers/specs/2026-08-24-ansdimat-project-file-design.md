# Формат `.ansdimat` — обмен журналами ОФР

Дата: 2026-08-24

## Задача

Сейчас журнал уходит наружу текстом: `handleShare` в `screens/PumpingTestProcessing/ProjectsScreen.js`
собирает шапку и строки «время — понижение» и отдаёт их в `Share.share({ message })`.
Получатель видит таблицу, но не может вернуть её в приложение: обратного пути нет
вообще. Скважины, фазы замеров, продолжительность откачки, результаты расчёта в текст
не попадают.

Нужен обмен полноценными проектами: файл, который система узнаёт по расширению, отдаёт
приложению по двойному нажатию и который разворачивается в рабочий журнал.

## Решение

Собственный тип файла `.ansdimat` — JSON-конверт с версией и контрольной суммой.
Приложение объявляет себя владельцем типа в iOS и Android, принимает открытый файл
через `Linking`, показывает, что именно приехало, и разворачивает в SQLite.

Отвергнутые варианты:

- **Облачная ссылка `https://…/p/<id>`** с веб-превью для тех, у кого нет приложения.
  Требует бэкенда, хостинга, associated domains и публичного доступа к чужим данным —
  это отдельный проект, не часть формата файла.
- **Deep-link с данными в URL** (`ansdimat://import?data=<base64>`). Не нужна регистрация
  типа, но проект — это килобайты; мессенджеры режут и переносят длинные ссылки.

Новых зависимостей не требуется: `expo-file-system`, `expo-sharing` и
`expo-document-picker` уже объявлены в `package.json` (и до сих пор не использовались),
`Linking` — из ядра React Native. sha-256 реализуется на чистом JS, чтобы разбор формата
проверялся Jest без нативных моков.

## Формат файла

```
Расширение   .ansdimat
MIME         application/vnd.ansdimat.project+json
UTI (iOS)    com.omnion.ansdimat.project   (conforms to public.data, public.json)
Кодировка    UTF-8, JSON с отступом 2
Имя файла    <санитайзнутое название>.ansdimat
```

```jsonc
{
  "format": "ansdimat.project",   // отличает свой файл от произвольного JSON
  "formatVersion": 1,
  "app": { "name": "Ansdimat", "version": "1.0.0", "platform": "ios" },
  "exportedAt": "2026-08-24T10:00:00.000Z",
  "checksum": "sha256:<hex от canonicalJson(payload)>",
  "payload": {
    "sourceId": "<uuid проекта у отправителя>",
    "name": "Куст №3",
    "ofrType": "cluster",
    "units": {                       // в чём лежат числа ниже
      "time": "min", "distance": "m", "flow": "m3_day",
      "transmissivity": "m2_day", "drawdown": "m"
    },
    "Q": 500,
    "pumpingDuration": 1440,
    "finalDrawdown": 3.2,
    "results": { "T": 125.4, "slope": 0.42, "method": "cooper-jacob" },
    "createdAt": 1690000000000,
    "wells": [
      { "sourceId": "…", "name": "1w", "role": "pumping",
        "distance": 0.1, "finalDrawdown": 4.2, "lat": null, "lon": null, "order": 0 }
    ],
    "measurements": [
      { "t": 1, "s": 0.35, "phase": "pumping", "wellSourceId": "…", "order": 0 }
    ]
  }

```

### Решения по содержимому

**Числа только в базовых единицах, не в пользовательских.** Текстовый экспорт отдаёт
значения через `fromBase(...)`, то есть в единицах отправителя. Для файла это ловушка:
получатель с другими настройками прочитает чужие числа как свои и получит расчёт,
отличающийся в разы.

Чтобы правило не держалось на честном слове, файл объявляет свои размерности сам —
блоком `units` внутри `payload`. Обязанности разделены так:

| Шаг | Что происходит |
|---|---|
| Ввод в приложении | `toBase` в `DataProcessingScreen` → в SQLite базовые единицы |
| Выгрузка | числа копируются как есть, `units` объявляет базовые |
| Разбор файла | числа приводятся к базовым по объявленному в `units` |
| Импорт | в SQLite ложатся базовые |
| Показ | `fromBase` переводит в размерности того, кто открыл журнал |

Пока обе стороны в базовых, приведение при разборе тождественно — числа совпадают до
бита. Но если файл придёт в футах и сутках, получатель это увидит и пересчитает, а не
положит футы в базу под видом метров. Неизвестная размерность — отказ (`invalid`), а не
молчаливая подстановка базовой: неизвестный масштаб чисел хуже отсутствия файла.

Блок `units` лежит внутри `payload`, а не рядом с ним, — значит, покрыт контрольной
суммой. Иначе правка одного слова в файле растянула бы весь журнал в 3.28 раза, и
ничто бы этого не заметило.

Отсутствие блока читается как «базовые»: так разбираются файлы, выгруженные до его
появления, и это верно — базовыми они и были.

Наклон прямой C (`results.slope`) — понижение на логарифмический цикл, то есть величина
понижения; так его и показывает экран обработки. Координаты скважин в градусах и
пересчёту не подлежат.

**`checksum`** считается от канонического JSON поля `payload`: ключи отсортированы по
возрастанию, без пробелов и переводов строк. Порча при пересылке ловится до записи в
базу, а не всплывает кривым графиком через неделю.

**`starred` не переносится.** Избранное — личная пометка получателя, а не свойство
журнала.

**`sourceId` у проекта и скважин** сохраняет исходные идентификаторы: по ним ищется
дубликат при повторном импорте, а `wellSourceId` у замера связывает его со скважиной
внутри файла, не завися от того, какие идентификаторы будут выданы при импорте.

### Совместимость версий

`formatVersion` больше текущей — импорт отклоняется с сообщением «файл создан более новой
версией приложения». Молчаливый разбор половины полей хуже честного отказа: журнал
выглядел бы импортированным, а часть данных потерялась бы без следа.

## Модули

Разбор формата не знает ни про SQLite, ни про нативные вызовы — поэтому проверяется
целиком в Jest.

```
share/
  format.js         константы: magic, версия, mime, uti, расширение, коды ошибок
  sha256.js         sha-256 на чистом JS
  canonicalJson.js  детерминированная сериализация
  projectFile.js    buildProjectFile() / parseProjectFile()
  exportProject.js  сборка файла в кэш + системное «Поделиться»
  incomingFile.js   распознавание входящего url, чтение content:// и file://
  ImportContext.js  провайдер «есть файл на импорт»
  __tests__/
components/
  ImportProjectDialog.js
```

Правки в существующих файлах: `app.json`, `db/schema.js`, `db/projects.js`,
`screens/PumpingTestProcessing/ProjectsScreen.js`, `App.tsx`, `Localization.js`.

## Регистрация типа в ОС

Нативные каталоги `android/` и `ios/` в `.gitignore` — сборка идёт через prebuild,
поэтому вся нативная настройка живёт в `app.json`.

### iOS

`UTExportedTypeDeclarations` объявляет тип `com.omnion.ansdimat.project`, наследующий
`public.data` и `public.json`, с расширением `ansdimat` и своим MIME.
`CFBundleDocumentTypes` заявляет права на него с `LSHandlerRank: Owner` и
`CFBundleTypeRole: Editor`. После этого Files, Почта, AirDrop и мессенджеры показывают
«Открыть в Ansdimat», а иконка документа выводится из иконки приложения.

`LSSupportsOpeningDocumentsInPlace` = `false`. При `true` iOS отдаёт security-scoped URL,
который требует `startAccessingSecurityScopedResource`; React Native этого не делает, и
чтение падает. При `false` система кладёт копию в `Inbox/`, откуда файл читается обычным
способом и удаляется после импорта.

### Android

Intent-filter на `ACTION_VIEW` с категориями `DEFAULT` и `BROWSABLE`, схемами `file` и
`content`, `mimeType` `*/*` и набором `pathPattern`: `.*\\.ansdimat`, `.*\\..*\\.ansdimat`
и далее до четырёх точек — `pathPattern` не умеет «оканчивается на», и повторение шаблона
это стандартный обход.

Ограничение, которое принимаем осознанно: `content://`-ссылки от системного
DocumentsProvider (Загрузки, Google Drive) прячут имя файла в непрозрачный путь, и
`pathPattern` по ним не срабатывает — приложения не будет в списке «Открыть с помощью».
Поймать их можно только фильтром на `application/octet-stream` без `pathPattern`, но тогда
приложение вылезает в этот список для любого файла неизвестного типа. Вместо этого —
явная кнопка «Импорт из файла» через `DocumentPicker`, которая работает всегда.

Комбинация покрывает вложения из мессенджеров и обычные файловые менеджеры, где имя
файла в пути присутствует.

## Экспорт

Иконка «поделиться» в карточке журнала открывает меню из двух пунктов:

- **Файл проекта (.ansdimat)** — новый путь, основной;
- **Таблица замеров (текст)** — нынешний `handleShare` остаётся без изменений.

Текстовый экспорт сохраняется намеренно: вставить журнал в отчёт — отдельная живая
задача, ради которой его и переписывали с `JSON.stringify` на таблицу.

Файл пишется в `FileSystem.cacheDirectory` и отдаётся через `Sharing.shareAsync` с
указанием `mimeType` и `UTI`. Если `Sharing.isAvailableAsync()` возвращает `false`
(веб-сборка) — скачивание через Blob.

## Импорт

### Приём файла

`Linking.getInitialURL()` при старте и подписка на событие `url` для случая, когда
приложение уже запущено. Android-ссылки `content://` копируются в кэш через
`copyAsync` и читаются оттуда: прямое чтение `content://` местами капризничает.

Файл разбирается и проверяется до любого показа: сначала magic и версия, затем
контрольная сумма, затем схема. Диалог видит уже разобранные данные.

### Место в дереве компонентов

`ImportProvider` живёт в `App.tsx` рядом с остальными провайдерами, диалог рисуется
поверх навигатора. Файл может прилететь на любом экране, в том числе пока показывается
заставка, — поэтому приём не может жить внутри экрана.

### Диалог

Показывает, что именно приехало: название, тип ОФР, дебит, число скважин, число замеров
откачки и восстановления, дату экспорта. Импорт — осознанное действие, а не «принять
неизвестно что».

### Дубликаты

Миграция v11 добавляет `projects.source_id` и индекс по нему. Совпадение ищется условием
`id = sourceId OR source_id = sourceId`: второе ловит повторный импорт того же файла,
первое — случай, когда у обоих устройств один аккаунт и журнал уже приехал синхронизацией.

Найден дубликат — три действия: **Заменить существующий**, **Создать копию**,
**Открыть имеющийся**. Не найден — просто **Импортировать**.

`source_id` серверу не отправляется: `toRemote` в `sync/tables.js` перечисляет поля явно,
поэтому миграция бэкенда не нужна.

### Запись

Одной транзакцией в `db/projects.js`. Проект, скважины и замеры получают новые UUID,
`wellSourceId` замеров перекладывается на выданные идентификаторы скважин, всё помечается
`dirty = 1` — журнал уедет на сервер как собственный. Режим «заменить» удаляет прежние
скважины и замеры проекта и записывает новые, сохраняя идентификатор проекта, чтобы
синхронизация увидела правку, а не новую запись.

После импорта — переход на `DataProcessing` с идентификатором журнала.

## Обработка ошибок

Каждый отказ получает свой код и своё сообщение:

| Код | Когда | Что видит пользователь |
|---|---|---|
| `not-ansdimat` | нет magic-строки | файл не является проектом АНСДИМАТ |
| `too-new` | `formatVersion` больше текущей | обновите приложение |
| `corrupted` | не разбирается JSON, не сходится сумма | файл повреждён при передаче |
| `invalid` | схема не сходится | файл повреждён или неполон |
| `read-failed` | не прочитался с диска | не удалось прочитать файл |

## Тестирование

Репозитории уже проверяются на настоящем SQLite через `node:sqlite`
(`db/__tests__/repositories.test.js`) — импорт проверяется там же, по-настоящему.

- `sha256.test.js` — известные векторы, юникод, длинные строки;
- `canonicalJson.test.js` — порядок ключей не влияет на результат;
- `projectFile.test.js` — round-trip, отклонение чужого JSON, битой суммы, будущей версии,
  обрезанного файла; единицы не пересчитываются;
- `importProject.test.js` — развёртывание в SQLite, режимы копии и замены, целостность
  связи скважина↔замер, обе фазы замеров, пометка `dirty`;
- `incomingFile.test.js` — какие url считаются своими.

## Локализация

Все новые строки добавляются в блоки `ru` и `en` файла `Localization.js`.

## Вне охвата

Облачные ссылки и веб-превью, перенос точек полевого дневника, шифрование и пароль на
файл, сжатие содержимого.
