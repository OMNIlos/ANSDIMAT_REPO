# Полная синхронизация с профилями на бесплатном Supabase

Дата: 2026-09-13

## Задача

«Настроить полную синхронизацию с профилями, которая возможна с free
Supabase». Всё, что человек заводит на одном устройстве, должно появляться на
другом устройстве под тем же аккаунтом — без ручных нажатий и без потерь.

Решения, принятые с заказчиком:

- синхронизируется **всё, включая вложения** — фото и голосовые заметки точек;
- **один владелец на устройство**: данные, созданные без входа, при первом
  входе уходят в аккаунт; при входе в другой аккаунт приложение предлагает
  убрать с устройства данные прежнего.

Смежные правки того же дня — в
[`2026-09-13-field-fixes-2-design.md`](2026-09-13-field-fixes-2-design.md).

---

## Что есть сейчас

Обмен уже работает для четырёх таблиц: `projects` (вместе с `params`), `wells`,
`measurements`, `observation_points` — движок pull/push в
[`sync/engine.js`](../../../sync/engine.js), описание таблиц в
[`sync/tables.js`](../../../sync/tables.js), серверная схема и RLS в
`supabase/migrations/`. Удаление мягкое, `updated_at` ставит сервер.

Не синхронизируются:

- **вложения точек** — таблица `point_attachments` и файлы живут только на
  устройстве (в схеме v13 это записано прямым текстом);
- **профиль** — строка `profiles` заводится триггером при регистрации, но
  приложение её не читает и не пишет;
- **настройки** — единицы в SQLite, язык и тема в AsyncStorage.

Найденные дефекты существующего движка:

| # | Дефект | Последствие |
|---|--------|-------------|
| 1 | Приём — одна страница по 1000 строк с курсором `updated_at > отметка`. Строки одной отправки получают одинаковое серверное время (`now()` — время начала транзакции) | граница страницы режет пачку с одинаковым временем, хвост пачки на другом устройстве не появится **никогда** |
| 2 | Отправка — одна пачка по 200 строк за обмен | журнал в 5000 замеров уходит за 25 обменов, а обмены идут раз в 15 минут |
| 3 | Триггер `touch_updated_at` стоит только `before update`; при вставке остаётся время телефона | новая строка с устройства с отстающими часами может оказаться «старше» курсора другого устройства и не доехать до него |
| 4 | Расхождение определяется как «локальная строка грязная и `updated_at` не совпадает с серверным». Локальное время и серверное не совпадают никогда | «правка → обмен → правка → обмен» даёт ложное «Есть расхождения» на собственную же прошлую отправку |
| 5 | Нерешённое расхождение останавливает курсор | каждый следующий обмен заново качает всё, что пришло после спорной строки, пока человек не ответит |
| 6 | `scheduleSync` объявлен, но не вызывается нигде | правки уходят только при входе, возврате из фона (не чаще раза в 15 минут) и по кнопке |
| 7 | `replaceMeasurements` при каждом сохранении помечает грязным весь журнал | сохранение одной строки гонит на сервер тысячи неизменённых замеров и умножает ложные расхождения |
| 8 | `resetSyncState` не вызывается; смена аккаунта не обрабатывается | строки прежнего аккаунта при отправке упираются в RLS, отправка падает на каждом обмене навсегда |
| 9 | Одна строка, отклонённая сервером (например, вторая опытная скважина в проекте из-за уникального индекса), роняет всю отправку | обмен стоит, пока строку не исправят руками |

## Подходы

- **A. Достроить свой движок pull/push — выбран.** Таблицы, Storage и RLS в
  Supabase, локальная SQLite как сейчас. Без новых сервисов и нативных модулей
  (всё нужное — `expo-file-system`, `@supabase/supabase-js` — уже в сборке),
  работает без связи, укладывается в бесплатный тариф. Изменения только в JS:
  новая нативная сборка не нужна. Корректность на нас — закрывается тестами.
- **B. PowerSync или ElectricSQL поверх Supabase.** Зрелая синхронизация, но
  это ещё один сервис со своими лимитами и аккаунтом, переписанный слой базы
  и новая нативная сборка — несоразмерно задаче.
- **C. Realtime без локальной базы.** Приложение для поля обязано работать без
  связи. Не подходит.

Мгновенная доставка через Realtime в этот объём не входит: для полевого
сценария «снял на телефоне — открыл на планшете» хватает обмена при открытии
и раз в несколько минут. Добавляется позже, не меняя модели данных.

## Что синхронизируется

| Данные | Где на устройстве | Где на сервере |
|--------|-------------------|----------------|
| Журналы ОФР с исходными данными | `projects` | `projects` |
| Скважины | `wells` | `wells` |
| Замеры | `measurements` | `measurements` |
| Точки дневника | `observation_points` | `observation_points` |
| Метаданные вложений | `point_attachments` | `point_attachments` (новая) |
| Файлы фото и голоса | `documents/attachments/` | Storage, bucket `attachments` (новый) |
| Профиль: имя, организация | `settings` (кэш) | `profiles` |
| Общие настройки: единицы, язык, моноширинные цифры | `settings`, AsyncStorage | `profiles.settings` (новая колонка) |

Не синхронизируются — это настройки устройства, а не человека: тема
(телефон в тёмной, планшет в светлой — нормальная картина), адаптация под
планшет, автоопределение координат.

## Сервер

Одна миграция `supabase/migrations/20260913120000_full_sync.sql`.

### Серверное время и при вставке

Триггеры `*_touch` на `projects`, `wells`, `measurements`, `observation_points`,
`profiles` пересоздаются как `before insert or update`. Время из запроса
игнорируется всегда — закрывает дефект 3.

### Таблица `point_attachments`

```sql
create table public.point_attachments (
  id           uuid primary key,
  owner_id     uuid not null references auth.users on delete cascade,
  point_id     uuid not null references public.observation_points on delete cascade,
  kind         text not null check (kind in ('photo', 'audio')),
  storage_path text not null,
  content_type text not null,
  size_bytes   bigint,
  duration     integer,
  waveform     text,
  recorded_at  timestamptz not null,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  deleted_at   timestamptz,
  constraint attachments_path_owner check (storage_path like owner_id::text || '/%')
);
```

Индексы `(owner_id, updated_at)` и `(point_id)`. RLS — как у замеров: видит и
меняет владелец, а вставка дополнительно проверяет, что точка принадлежит ему
же. Гранты `select, insert, update, delete` роли `authenticated`.

### Bucket `attachments`

Приватный. Путь файла — `<uid>/<id вложения>.<расширение>`. Лимит файла 25 МБ
(на тарифе потолок 50 МБ; 25 МБ — это почти час голоса в новом формате),
разрешённые типы `image/*` и `audio/*`.

Политики на `storage.objects` для `select`, `insert`, `update`, `delete`:
`bucket_id = 'attachments' and (storage.foldername(name))[1] = auth.uid()::text`.
Чужую папку нельзя ни прочитать, ни перезаписать.

### Профиль

`alter table public.profiles add column settings jsonb not null default '{}'`.
Существующие политики «профиль виден и правится владельцем» и грант `update`
покрывают новую колонку.

### Применение

Миграция проверяется на локальном Supabase (`supabase start`, если поднимется
Docker) тестами RLS. В облачный проект `iokljcwtrfejbzzyykug` применяется
`supabase db push` **только после отдельного разрешения заказчика**.

## Устройство

### Схема SQLite v14

- `projects`, `wells`, `measurements`, `observation_points`: колонки
  `server_updated_at TEXT` — версия строки на сервере, от которой шла последняя
  правка (NULL — строка на сервере ещё не была), и `sync_error TEXT` — почему
  сервер отклонил строку.
- `point_attachments`: `updated_at`, `deleted_at`, `dirty`, `server_updated_at`,
  `sync_error`, `content_type`, `size`, `file_state`. Существующие вложения
  получают `dirty = 1`, `updated_at = recorded_at`, `file_state = 'local'` —
  и уезжают на первом обмене.
- Новая таблица `sync_conflicts (table_name, row_id, remote_json,
  remote_updated_at, detected_at)`, ключ `(table_name, row_id)`.

`file_state` у вложения:

| Значение | Файл на устройстве | Файл в Storage |
|----------|--------------------|----------------|
| `local` | есть | нет — ждёт загрузки |
| `synced` | есть | есть |
| `remote` | нет — скачается при открытии точки | есть |
| `removing` | нет | ещё есть — ждёт удаления |

### Отправка

Таблицы по порядку внешних ключей: журналы → скважины → замеры → точки →
вложения. В каждой — **пачками по 200 до конца** (дефект 2):

1. Берётся пачка `dirty = 1`, кроме строк со спором и строк с `sync_error`.
   У вложений — только те, чей файл уже в Storage или которые удалены.
2. `upsert(...).select('id, updated_at')` — сервер возвращает свою версию.
3. Каждая строка помечается чистой **условно**:
   `UPDATE … SET dirty = 0, server_updated_at = ? WHERE id = ? AND updated_at = ?`
   с локальным `updated_at`, прочитанным на шаге 1. Строка, которую поправили,
   пока пачка летела, остаётся грязной и уйдёт следующей.
4. Если пачку отклонила база (ограничение, внешний ключ), пачка переотправляется
   по одной строке; отклонённые получают `sync_error` и больше не
   отправляются, пока их не изменят. Остальные уходят (дефект 9).

**Файлы — раньше строк.** Вложение с `file_state = 'local'` сначала грузится в
Storage, и только потом его строка попадает в отправку: на другом устройстве не
появится вложение, файла которого ещё нет.

Загрузка на устройстве — `FileSystem.uploadAsync` на
`/storage/v1/object/attachments/<путь>` с `uploadType: BINARY_CONTENT` и
заголовком `x-upsert`: файл читается с диска потоком, без base64 в памяти
JS. В вебе — `supabase.storage.upload` из data-URI через Blob.

**Замеры — только изменившиеся** (дефект 7). В `replaceMeasurements`
`ON CONFLICT DO UPDATE … WHERE` меняет строку и ставит `dirty = 1`, только если
изменились `t`, `s`, порядок, фаза или скважина.

### Приём

Для каждой таблицы, **страницами по 500 до конца** (дефект 1):

- порядок `updated_at, id`, следующая страница — строго после последней пары
  `(updated_at, id)`: одинаковое время у сотни строк больше не режется границей
  страницы;
- запрос начинается **на 2 минуты раньше** сохранённой отметки. Транзакция,
  начатая раньше, но завершённая позже чужой, получает время меньше отметки —
  запас её ловит. Повторно пришедшие строки ничего не стоят: см. следующий
  пункт.

Каждая пришедшая строка:

| Состояние локальной строки | Действие |
|----------------------------|----------|
| `server_updated_at` равен пришедшему `updated_at` | пропуск — эта версия уже есть (в том числе эхо своей отправки, дефект 4) |
| нет строки или `dirty = 0` | применить, `server_updated_at` ← пришедший |
| `dirty = 1` и версия другая | спор: снимок серверной строки в `sync_conflicts`, локальная не трогается |

Отметка двигается по всем пришедшим строкам, спорные её не держат (дефект 5):
спор лежит в базе вместе со снимком и переживает перезапуск.

Пришедшее вложение: удалённое — стирает свой файл; новое или с другим путём —
`file_state = 'remote'`.

### Споры

- **«Оставить эту»:** `server_updated_at` ← версия из снимка, строка остаётся
  грязной и на следующей отправке перезаписывает серверную. Если сервер за это
  время снова изменился, приём заметит новый спор.
- **«С другого устройства»:** снимок применяется, `dirty = 0`.

Споры группируются: скважины и замеры — под своим журналом, вложения — под
точкой. Одно решение на группу: правка журнала на двух устройствах — это один
вопрос «какой журнал оставить», а не сотня карточек по замерам. В карточке
видно название журнала или точки и время обеих правок.

### Файлы на другом устройстве

Скачиваются **при открытии шторки точки**, а не все сразу: 5 ГБ исходящего
трафика в месяц — на весь проект. `FileSystem.downloadAsync` с
`/storage/v1/object/authenticated/attachments/<путь>` и заголовком авторизации;
в вебе — `supabase.storage.download` в data-URI. Пока файла нет — у снимка
заглушка с индикатором, у заметки неактивная кнопка; без связи — значок «нет
связи» вместо индикатора.

### Удаление

Мягкое везде. Удалённое вложение сразу стирает свой файл на устройстве:

- если строка на сервере не бывала (`server_updated_at` NULL) — строка просто
  удаляется, отправлять нечего;
- иначе строка уходит с `deleted_at`, затем файл удаляется из Storage
  (`file_state = 'removing'` до успеха — с повтором на каждом обмене).

`deletePoint` перестаёт удалять вложения жёстко: они помечаются удалёнными в
той же транзакции, что и точка, файлы стираются после неё.

### Профиль и общие настройки

Профиль — одна строка, поэтому без курсоров и снимков:

- **приём:** `select` своей строки; если версия изменилась, применяются
  значения тех полей, которые не правились локально;
- **отправка** правленых полей — оптимистично:
  `update … where id = uid and updated_at = <версия>` с `select`. Ноль строк —
  значит профиль изменили на другом устройстве: принять, наложить свои поля,
  повторить. Время телефона не участвует вовсе.

Кэш профиля и список правленых полей лежат в `settings` (`profileCache`,
`profileDirty`). Единицы, язык и моноширинные цифры, пришедшие с сервера,
применяются через `UnitsContext`, `LanguageContext` и экран настроек — на лету,
без перезапуска.

Имя и организация редактируются на экране аккаунта.

### Когда идёт обмен

| Событие | Что делается |
|---------|--------------|
| вход в аккаунт | полный обмен |
| правка данных | обмен через 5 с после последней правки |
| возврат из фона | обмен, если прошлый был больше минуты назад |
| приложение открыто | обмен раз в 5 минут |
| кнопка на экране аккаунта | обмен сразу |

Правки сообщают о себе через маленькое хранилище событий `sync/changes.js`:
репозитории `db/projects.js`, `db/wells.js`, `db/points.js`,
`db/attachments.js` и запись синхронизируемых настроек вызывают
`notifyLocalChange()`, `SyncProvider` слушает — тот же приём, что у
`components/chromeVisibility.js`.

После обмена, который что-то применил, то же хранилище рассылает
`remoteApplied`. Списки журналов и точек, главная и открытая шторка точки
перечитывают данные. Экран обработки журнала не перечитывается под руками — он
обновится при следующем открытии, как и сейчас.

### Владелец устройства

Ключ `syncOwnerId` в `settings`.

- **Первый вход** (`syncOwnerId` пуст): владельцем становится вошедший; всё
  созданное без входа уходит в его аккаунт.
- **Тот же аккаунт:** обычный обмен.
- **Другой аккаунт:** обмен не запускается. Диалог: «На устройстве данные
  другого аккаунта. Не отправлено: N. Убрать их с устройства и загрузить данные
  этого аккаунта?» — «Убрать и загрузить» / «Выйти». Уборка: строки
  синхронизируемых таблиц, файлы вложений, отметки, споры, кэш профиля; затем
  полный приём.
- **Выход:** данные и `syncOwnerId` остаются — как обещает диалог выхода.
- **Удаление аккаунта:** сначала удаляются его файлы в Storage, потом
  `delete_own_account`. Данные на устройстве остаются и становятся данными
  «без входа»: `server_updated_at`, отметки и споры сбрасываются, всё грязное,
  `syncOwnerId` пуст; вложения, файлов которых на устройстве нет, удаляются.

**Установки, обменивавшиеся до этой версии.** `syncOwnerId` у них пуст, но данные
уже принадлежат аккаунту. При первом запуске, если есть отметки обмена и
сохранённая сессия, владельцем записывается аккаунт этой сессии. Если сессии нет
и владелец неизвестен, первый вход назначает владельца; если отправка упрётся
в RLS (`42501`), показывается тот же диалог смены аккаунта.

### Экран аккаунта

Добавляются: поля «Имя» и «Организация»; строка «Файлы в облаке: N МБ» (сумма
размеров своих вложений); «Не отправлено файлов: N» с причиной, если загрузка
не удаётся; сгруппированные споры с названиями.

Статусы обмена: «Синхронизация…», «Данные актуальны», «Есть расхождения», «Нет
связи — повторю позже» (сетевой сбой не показывается красной ошибкой), «Не
удалось синхронизировать» с текстом ошибки сервера.

### Голосовые заметки меньше

Пресет записи — AAC моно 64 кбит/с (сейчас стерео 128 кбит/с): ~0,5 МБ в минуту
вместо ~1. Разборчивость речи не страдает, место в Storage вдвое дешевле.
Уже записанные заметки не перекодируются.

## Бесплатный тариф

Лимиты Free на сентябрь 2026 (supabase.com/pricing): база 500 МБ, файлы 1 ГБ,
файл до 50 МБ, 5 ГБ исходящего трафика и ещё 5 ГБ кэшированного, 50 000
активных пользователей, 2 активных проекта.

- **Лимиты общие на проект, а не на пользователя.** Строки весят копейки: журнал
  на 100 замеров — около 8 КБ. Место занимают файлы: снимок после сжатия
  0,6 — порядка 1 МБ, минута голоса — 0,5 МБ. 1 ГБ — это примерно тысяча
  снимков на всех.
- **Трафик** бережёт ленивая загрузка файлов и повторная отправка только
  изменённых замеров.
- **Проект засыпает после недели без обращений.** Обмен тогда отвечает «Нет
  связи»; проект просыпается при первом обращении или из панели Supabase.
  Кодом это не обходится — описывается в документации.
- **Резервных копий на Free нет.** Описывается в документации вместе с
  ручной выгрузкой (`supabase db dump`).

## Устройство кода

`sync/engine.js` вырос бы до тысячи строк, поэтому делится:

| Модуль | Отвечает за |
|--------|-------------|
| `sync/engine.js` | порядок шагов обмена, итог, отчёт об ошибках |
| `sync/rows.js` | приём и отправка строк по описанию из `sync/tables.js` |
| `sync/conflicts.js` | хранение, группировка и разрешение споров |
| `sync/files.js` (+ `files.web.js`) | загрузка, скачивание и удаление файлов вложений |
| `sync/profile.js` | профиль и общие настройки |
| `sync/owner.js` | владелец устройства, уборка при смене аккаунта |
| `sync/changes.js` | события «локальная правка» и «применены данные сервера» |
| `sync/tables.js` | + описание `point_attachments` |
| `sync/SyncContext.js` | когда запускать обмен, состояние для экранов |

Каждый модуль проверяется отдельно с поддельным клиентом Supabase — так уже
устроен `sync/__tests__/engine.test.js`.

## Обработка ошибок

- **Нет сети** — статус «Нет связи», повтор по следующему поводу из таблицы
  выше. Данные на устройстве не трогаются.
- **Сервер отклонил пачку** — переотправка по строке, отклонённые получают
  `sync_error`, остальные уходят.
- **Файл не загрузился** — остаётся `local`, счётчик неудачных попыток и
  причина видны на экране аккаунта; превышение размера и места называется
  прямо.
- **Истекла сессия** — `supabase-js` продлевает сам; для
  `uploadAsync`/`downloadAsync` токен берётся из `getSession()` перед каждым
  файлом.
- **RLS отказал на отправке** (`42501`) — диалог смены аккаунта, см. выше.

## Проверка

**Jest, движок с поддельным Supabase** (серверное время, одинаковые отметки,
страницы):

- 1500 строк с одинаковым `updated_at` доходят все при странице 500;
- эхо своей отправки не спор; настоящая правка с другого устройства — спор;
- спор не держит отметку и переживает перезапуск; оба варианта решения;
- отправка идёт пачками до конца; строка, изменённая во время отправки,
  остаётся грязной;
- отклонённая строка получает `sync_error` и не блокирует остальные;
- вложения: файл раньше строки; `remote` → скачивание; удаление с
  `removing` и повтором;
- профиль: оптимистичная запись, ноль строк → принять и повторить;
- владелец: первый вход, тот же аккаунт, другой аккаунт → уборка; удаление
  аккаунта → данные «без входа».

**Jest, репозитории:** `replaceMeasurements` не пачкает неизменённые замеры;
`deletePoint` помечает вложения удалёнными; миграция v14 на базе v13 с
вложениями.

**SQL на локальном Supabase** (если поднимется Docker): RLS `point_attachments`;
политики Storage — чужую папку не прочитать и не записать; время ставится
сервером и на вставке.

**Сквозной сценарий в веб-превью** — два браузерных контекста как два
устройства, по образцу `supabase/tests/e2e-sync.test.js`: журнал, точка со
снимком и голосом, профиль и единицы на первом — всё на втором; удаление на
втором — пропало на первом. Против облачного проекта — только с разрешения:
тест заводит аккаунты.

## Порядок работ

1. Серверная миграция и SQL-тесты.
2. Схема SQLite v14; репозитории: условная пометка замеров, мягкое удаление
   вложений, `notifyLocalChange`.
3. Движок строк: страницы, версии, споры, построчная переотправка.
4. Файлы вложений: загрузка, ленивое скачивание, удаление; пресет записи.
5. Профиль и общие настройки.
6. Владелец устройства и удаление аккаунта.
7. `SyncProvider`: расписание обмена, `remoteApplied`; экран аккаунта.
8. Документация `docs/supabase/` — новая миграция, лимиты, сон проекта,
   резервные копии.
9. С разрешения — миграция в облако и сквозная проверка.
